# Control de acceso a un servidor Fabric 26.1 en online-mode=false desde un sistema de cuentas propio (whitelist offline, mod de login propio, mods existentes, sincronización de whitelist, skins, toolchain Loom 26.1, desconexión con mensaje)

## Recomendación
Implementar A + C en un único mod server-side propio ('sobrinosdepepe-guard', Fabric 26.1, Java 25, Loom 1.17 con plugin net.fabricmc.fabric-loom) más un micro-mod cliente ('sobrinosdepepe-client') que el launcher instala junto con los demás mods. A: en ServerLoginConnectionEvents.QUERY_START el server manda un query 'sobrinosdepepe:auth' con nonce; el cliente responde con el token que el launcher le pasó por -Dsobrinosdepepe.token; el server valida contra POST /api/mc/verify del backend Next.js con un secreto que solo vive en config/sobrinosdepepe-guard.json del server (tokens firmados, TTL ≤5 min, one-time por jti, ligados al nombre canónico y al serverId), fuerza exact-match del nombre (case-sensitive porque el UUID offline depende del case) y desconecta con mensaje claro en cualquier otro caso (sin mod → 'usá el launcher'; pending → 'Tu cuenta está pendiente de aprobación'; banned → motivo). C: el mismo mod hace polling cada 60 s a GET /api/mc/allowlist (mismo secreto) y mantiene whitelist.json + kickea baneados online; mantener white-list=true y no dar OP a nadie (los OPs saltan la whitelist en offline-mode). Así el launcher jamás tiene credenciales de admin, el server no necesita RCON ni puertos extra ni API del panel, y aunque el mod fallara en cargar la whitelist vanilla sigue filtrando nombres. Skins: SkinRestorer 2.10.0+26.1 en el server con autoFetch mojang (quien tenga nombre Mojang lo ve gratis) y, para skins subidas al launcher, el backend expone la PNG por URL y el mod (o un comando por API del panel) ejecuta '/skin set web (classic|slim) "<url>" <jugador>' (requiere MineSkin API key, gratis). Plan B sin escribir Java: EasyAuth 3.4.4 (login por contraseña dentro del juego, cuentas creadas desde el backend vía POST /api/client/servers/{id}/command del panel Pterodactyl) + whitelist vanilla; es más fácil pero peor UX y acopla el backend a la API del panel. Descartar Velocity+LimboAuth (necesita proxy propio y firewall del backend, inviable en hosting compartido) y AuthMe (plugin Paper).

## Hallazgos (22)

1. [high] UUID offline = UUID v3 (MD5) de la cadena "OfflinePlayer:"+username. El servidor vanilla IGNORA el UUID que manda el cliente en el paquete Login Start ("Player UUID: Unused by the vanilla server"). Calculado hoy: PEPE -> 7a067f19-b48d-3c6e-9039-8f37f64def1f, Chichon -> 5f1bb3e1-3a21-3c39-a409-e50842f7df31, Titit0N -> 7bc394ba-c092-3432-b0b3-57a16c894f33, Luquitas1410 -> 9c4d6396-daf9-3c3c-9eb3-93fe87cb87b7. El uuid 5b071e1f-3a11-4f28-... que muestra TLauncher es un v4 generado en el cliente y NO es el que usa el servidor.
   - fuente: https://minecraft.wiki/w/Universally_unique_identifier ; https://minecraft.wiki/w/Java_Edition_protocol/Packets (Login Start) ; cálculo local con Python (md5 + version nibble 3 + variant RFC4122)
   - notas: Verificado hoy. Es case-sensitive: "PEPE" y "Pepe" dan UUIDs distintos → inventario/ender chest/stats distintos. El backend debe fijar el nombre canónico exacto y el launcher debe lanzar el juego con ese --username exacto.

Formato: [{"uuid":"<uuid con guiones>","name":"<nombre>"}]. Editar a mano requiere /whitelist reload. Los OPs siempre entran aunque no estén en la whitelist (Java Edition).
   - fuente: https://minecraft.wiki/w/Whitelist.json

Consecuencia: NO dar OP a jugadores en offline-mode — quien se conecte con el nombre de un OP con un cliente cracked entra saltando la whitelist y con permisos de admin.

20. [high] Diseño A concreto (viable con las APIs verificadas). Canal: Identifier 'sobrinosdepepe:auth' v1. Server→cliente en QUERY_START: {u8 version=1, byte[16] nonce, utf8 serverId}. Cliente→server: {u8 version=1, utf8 token (≤4 KB)} donde token = lo que el launcher recibió del backend en POST /api/launcher/session (JWT firmado Ed25519/ES256, TTL ≤ 5 min, claims: sub=accountId, name=nombre canónico exacto, uuid=UUID offline v3, srv=serverId, jti=id único). Server: si !understood → disconnect("Necesitás entrar con el launcher de SOBRINOS DE PEPE"); si understood → future = POST https://backend/api/mc/verify {token, nonce, ip} con header X-Server-Secret (secreto solo en config del server) → backend valida firma+exp, marca jti como usado (one-time, anti-replay), devuelve {ok, name, uuid, status: approved|pending|banned}; el mod compara name con el nombre pedido en el login (exact match) y desconecta con mensaje según status; synchronizer.waitFor(future). Fallback si el backend no responde: verificar la firma offline con la clave pública embebida y aceptar si exp válido (aceptando el riesgo de replay durante la caída) o rechazar con "Servidor de cuentas no disponible" (configurable).
   - fuente: APIs verificadas en https://github.com/FabricMC/fabric/tree/26.1/fabric-networking-api-v1 ; formato de paquetes según https://minecraft.wiki/w/Java_Edition_protocol/Packets
   - notas: Importante: en offline-mode la conexión Minecraft NO va cifrada (no hay encryption request), así que el token viaja en claro por TCP: por eso TTL corto + one-time (jti) + binding a serverId. El launcher nunca tiene credenciales de admin: solo su sesión de usuario; el secreto X-Server-Secret solo lo tiene el server; la clave privada de firma solo el backend.

## Riesgos
- En offline-mode la conexión Minecraft no está cifrada: el token del login query viaja en claro por TCP. Mitigación obligatoria: TTL ≤5 min, one-time (jti) validado por el backend, binding a serverId; aún así alguien en la misma LAN podría intentar replay dentro de la ventana si el backend está caído y se usa el fallback offline.
- Si el backend no responde, nadie puede entrar (o se degrada a verificación offline de firma). Definir política explícita y timeouts (p.ej. 5 s) para no colgar el login.
- Nombres case-sensitive: si el usuario elige 'Pepe' y luego entra como 'PEPE' pierde inventario (UUID offline distinto). El backend debe fijar el nombre canónico y el launcher pasar exactamente ese --username; los 5 jugadores actuales deben registrarse con su nombre EXACTO actual para conservar inventario/progreso.
- Los OPs saltan la whitelist en Java Edition: en offline-mode un OP con nombre conocido es takeover total. No dar OP a jugadores; administrar por consola del panel.
- Requiere que Minehost permita subir mods por FTP y que el server tenga salida HTTPS al backend (normal, pero no verificado). El panel puede ser Pterodactyl o Multicraft según nodo; si se necesita ejecutar comandos desde el backend hay que confirmar que la API del panel esté habilitada (Multicraft la deshabilita por defecto).
- Cada versión de Minecraft (26.1 → 26.2/26.3) exige recompilar los mods propios y esperar Fabric API/SkinRestorer/etc. Congelar el server en 26.1 hasta tener el pipeline de build probado.
- Toolchain nueva para el usuario: JDK 25, Gradle 9.x, Loom 1.17, mixins/accessors; el primer setup y decompilación tarda y hay curva de aprendizaje Java (estimado 2–4 días).
- Skins por URL dependen de MineSkin (tercero) para la firma; Mojang API tiene rate limits y cache. TLauncher (tlskincape) deja de funcionar como sistema de skins al migrar; hay que comunicarlo.
- Al activar el mod, cualquier cliente sin el mod (TLauncher, vanilla cracked) queda afuera: toda la comunidad debe migrar al launcher el mismo día (planificar corte).
- El mod cliente introduce un requisito de Fabric API en el cliente (ya está) y se debe versionar junto al launcher: si el manifest actualiza el mod cliente y el server no (o viceversa), el protocolo v1 debe seguir compatible; incluir el campo version en los paquetes.
- Opción D (Drasl + authlib-injector) queda en zona gris respecto de la restricción del usuario de no reemplazar la autenticación oficial; solo considerar si el usuario la relaja explícitamente.

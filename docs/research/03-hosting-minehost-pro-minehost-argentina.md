# Hosting minehost.pro / Minehost (Argentina): panel, API, puertos, planes, DNS/SRV y Server List Ping de quemandan.minehost.pro

## Recomendación
Integrar el launcher/backend con Minehost exclusivamente a través de la Client API de Pterodactyl (https://pterodactyl.minehost.com.ar/api/client), no con RCON ni con puertos extra (no existen). Flujo: (1) el admin crea una API key en https://pterodactyl.minehost.com.ar/account/api y obtiene el identifier del server (8 chars en la URL /server/xxxxxxxx); (2) la key vive SOLO en el backend (Next.js API o ASP.NET; nunca en el launcher); (3) al autorizar un usuario en el panel de admin, el backend hace `POST /api/client/servers/{id}/command` con `{"command":"whitelist add <nick>"}` (y `whitelist remove` / `ban` / `kick` para bans), con reintento si recibe 502 (server apagado) y reconciliación periódica leyendo `GET .../files/contents?file=/whitelist.json` y `/banned-players.json`; opcionalmente usar `GET .../resources` para saber si el server está running y `POST .../power` para reiniciarlo desde el panel de admin. Rate limit 256/min sobra. (4) Para el indicador "Servidor online ●" y jugadores online, el launcher hace directamente: resolver SRV `_minecraft._tcp.quemandan.minehost.pro` (DnsClient en .NET / dns.resolveSrv en Node) -> Server List Ping a sv36:25445 con timeout 3 s -> mostrar online/max y MOTD; sin backend ni credenciales. Siempre resolver SRV en runtime porque el target del nodo puede cambiar (TTL 300 s). (5) Mantener online-mode=false (obligatorio con cuentas TLauncher free) y tratar la whitelist como filtro, no como autenticación: la seguridad real la aporta el login del launcher; si querés bloquear a alguien que conozca un nick whitelisteado, hace falta además un mod Fabric server-side de verificación (token de sesión emitido por tu backend y validado en el login del jugador; el contenedor puede salir a Internet aunque no reciba conexiones entrantes), o al menos rotar nicks/bans rápido desde el panel. (6) Antes de diseñar en firme, que el usuario confirme en su Pterodactyl: que puede crear API keys, la imagen Docker/Java del Startup, cuántas allocations tiene en Network y el cupo de Backups; y que exporte un backup propio por SFTP (puerto 2022) porque Minehost borra archivos 6 días después de una suspensión.

## Riesgos
- La API key de Pterodactyl da control TOTAL del server (archivos, power, consola, borrar mundo): si se filtra (repo, launcher, logs) el server queda comprometido. Debe vivir sólo en el backend, en variable de entorno, con rotación; nunca en el .exe del launcher.
- Minehost podría tener deshabilitada la creación de API keys para clientes (no verificable sin login) o cambiar el panel/tema; si /account/api no permite crear keys, la única alternativa automatizable es SFTP (puerto 2022, escribir whitelist.json) y pedir a soporte que confirme.
- `POST .../command` devuelve 502 si el server está apagado o reiniciando: el backend necesita cola con reintentos e idempotencia (whitelist add repetido es inocuo). Además si Minehost migra el server a otro nodo, cambia el target del SRV y el host SFTP; el identifier de Pterodactyl se mantiene.
- Sin RCON ni puertos adicionales: ningún mod server-side puede exponer un endpoint HTTP entrante. Cualquier comunicación server->backend debe ser saliente (el mod hace polling/push a tu API). Verificar que el contenedor tenga egress a Internet (casi seguro sí, ya que descarga mods/JARs).
- Whitelist en online-mode=false es por nombre: cualquiera que conozca un nick autorizado entra con cualquier launcher offline. La KB de Minehost (45/46) lo advierte y su remedio son plugins de Paper, inaplicables en Fabric. Si la comunidad crece o se filtra la IP/puerto (es público: sv36.minehost.pro:25445, y el SRV es consultable por cualquiera), hace falta autenticación adicional del lado del server.
- Backups: no hay evidencia de backups incluidos; el servicio es prepago a 30 días, se suspende el día 30 y a los 6 días borran los archivos. Sin backup externo automatizado (API /backups o SFTP) se puede perder el mundo por un pago atrasado.
- La documentación de Minehost es de la era Multicraft y no coincide con el panel Pterodactyl actual; el soporte es por chat/Discord sin SLA formal y la operación es unipersonal (riesgo de dependencia de una persona). Los dominios minehost.pro / panel.minehost.pro / cp.minehost.pro devolvían 522/530 hoy.
- Java 25 / Fabric 26.1 funcionan hoy porque el server ya corre 26.1, pero la disponibilidad de imágenes Java futuras (p.ej. Java 26 para Minecraft 26.x posteriores) depende de que Minehost actualice su egg; el plan de actualizaciones del launcher debe poder pinear la versión de Minecraft hasta que el host la soporte.
- Protocolo observado 775 (no 773): el launcher no debe hardcodear el protocolo para nada; para el SLP usar -1 y leer el protocolo que reporta el server, y para la compatibilidad cliente/servidor comparar contra el version JSON de Mojang.

## Preguntas para el usuario
- Entrá a https://pterodactyl.minehost.com.ar/account/api: ¿te deja crear una API key? Y en tu server, ¿cuál es el identifier de 8 caracteres de la URL (/server/xxxxxxxx)? Esto decide si la integración de whitelist se hace por Client API (recomendado) o hay que caer a SFTP/soporte.
- En Pterodactyl > tu server > Network: ¿cuántas allocations ves y hay botón para agregar otra? (si hay una segunda, RCON se vuelve una opción; si no, se descarta definitivamente). Y en Startup: ¿qué 'Docker Image' figura (java_25?) y qué variables/egg ('Fabric', versión) muestra?
- ¿Qué plan/RAM tenés (lo muestra el dashboard: Memory X / Y GiB) y qué dice la pestaña Backups (cupo N of M)? Determina si el server aguanta los 14 mods con más jugadores y si hace falta implementar backups externos en el plan.
- ¿Estás dispuesto a hospedar el backend (Next.js API o ASP.NET) en un servicio propio para guardar la API key de Pterodactyl, o preferís que el launcher/admin hable con Pterodactyl directo desde tu PC (menos seguro y sin panel web)?
- ¿Querés que la seguridad de acceso dependa sólo de login del launcher + whitelist por nick, o aceptás incluir un mod Fabric server-side propio (validación de token en el login del jugador) para que un nick autorizado no pueda ser usado desde otro launcher offline? Cambia el alcance (hay que desarrollar y mantener un mod del lado del server).

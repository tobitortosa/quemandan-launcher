# Crítica adversarial del plan de ChatGPT para el launcher privado de Minecraft (26.1 + Fabric, offline-mode, 5-20 jugadores)

## Recomendación
Rehacer el plan alrededor del núcleo técnico y del tamaño real del problema (5-20 amigos, todos offline, server 26.1 en Minehost): (1) Fase 0 = spike sin UI que lance Minecraft 26.1 + Fabric Loader 0.19.5 + los 13 mods (sin maplink) con JRE Temurin 25 desde una carpeta aislada y entre al server como PEPE con inventario intacto; ahí se resuelven los riesgos reales (version JSON con rules, assets, classpath Fabric, Java 25, SRV). (2) Manifest en formato mrpack/Modrinth (URLs de cdn.modrinth.com + hashes, sides client/server, archivos Mojang siempre desde Mojang, JRE desde Adoptium) generado por un script TS; nada re-hosteado, créditos en el launcher. (3) Launcher con UI de un botón, progreso en bytes, logs/crash capturados, RAM automática, toggle Shaders, importación desde TLauncher, y auto-update (Velopack) desde la primera build distribuida. (4) Servidor: EasyAuth 3.4.4 + SkinRestorer 2.10.0 + whitelist; usernames reservados con el case exacto de los 5 jugadores actuales porque el UUID offline es MD5('OfflinePlayer:'+name) y el server ignora el UUID del launcher. (5) Backend y panel admin en Next.js (stack del usuario) sobre Postgres administrado (Neon/Supabase), nunca SQLite en Vercel ni C# en Vercel; el launcher debe poder JUGAR con sesión cacheada si el backend está caído. (6) Tirar del plan: panel admin dentro del .exe, panel de mods/subir modpack, anti-multicuenta por IP, login Microsoft, 4 repos y 4 proveedores de infra. (7) Distribución: aceptar el aviso de SmartScreen con instructivo (Azure Artifact Signing no está disponible en Argentina) y confiar en el auto-update para no re-descargar exes; firma OV solo si sobra presupuesto. (8) Posicionar el proyecto como instalador de modpack + control de acceso a un server privado; documentar que no distribuye archivos de Mojang ni implementa bypass, y que el usuario acepta conscientemente la zona gris del offline-mode.

## Hallazgos (37)

1. [high] Vercel NO tiene runtime oficial para C#/ASP.NET Core. Runtimes oficiales hoy: Node.js, Bun, Python, Rust, Go, Ruby, Wasm, Edge; community runtimes recomendados: Bash, Deno, PHP. Sí soporta imágenes OCI (containers) pero eso no arregla el problema del filesystem.
   - fuente: https://vercel.com/docs/functions/runtimes
   - notas: Verificado hoy. El plan combina 'API C#' con 'Vercel' y eso no cierra. Corrección: o el backend es TypeScript (Next.js route handlers, el stack real del usuario) y va a Vercel, o es C# y va a un VPS/Fly.io/Railway/Azure Container Apps. No mezclar.

2. [high] SQLite como DB en Vercel no funciona: las funciones tienen filesystem read-only con /tmp de hasta 500 MB efímero y no compartido entre instancias; cualquier escritura se pierde.
   - fuente: https://vercel.com/docs/functions/runtimes#file-system-support (cita: 'read-only filesystem with writable /tmp scratch space up to 500 MB'); https://vercel.com/kb/guide/is-sqlite-supported-in-vercel
   - notas: Verificado hoy. Corrección: Postgres administrado (Neon o Supabase, free tier alcanza sobrado para 20 usuarios) o SQLite solo si el backend vive en un único VPS/proceso persistente. El plan lista SQLite y Supabase 'más adelante' como si fueran etapas; elegir uno desde el día 1 (Postgres) evita migración.

3. [high] Minecraft 26.1 exige Java 25 (version JSON: javaVersion {component:'java-runtime-epsilon', majorVersion:25}). El JDK 17 que el usuario tiene en Downloads NO sirve para el cliente 26.1. Mojang publica el runtime 'java-runtime-epsilon' = 25.0.1 para windows-x64 (411 archivos, 105 MB raw / 81 MB lzma, formato por-archivo). Adoptium Temurin ofrece JRE 25.0.4.1+1 windows x64 como un único zip de 58 MB.
   - fuente: https://piston-meta.mojang.com/v1/packages/c27af223100c5a1a7c986b361170bc8bd71ff3e1/26.1.json ; https://piston-meta.mojang.com/v1/products/java-runtime/2ec0cc96c44e5a76b9c8b7c39df7210883d12871/all.json ; https://api.adoptium.net/v3/assets/latest/25/hotspot?os=windows&architecture=x64&image_type=jre
   - notas: Verificado hoy. El plan dice 'Java privado' sin versión; cualquier mención a Java 17 (o al fabric-installer + JDK 17 del usuario) es incorrecta para 26.1. Recomendación: descargar el zip de Adoptium (un archivo, sha256 en la API, licencia GPL+CE claramente redistribuible/descargable) en runtime/java/; el formato de Mojang (lzma por archivo) es más trabajo de implementar.

4. [high] El servidor 'quemandan.minehost.pro' NO tiene registro A; se resuelve por SRV: _minecraft._tcp.quemandan.minehost.pro -> sv36.minehost.pro puerto 25445. Un chequeo de 'Servidor online ●' contra quemandan.minehost.pro:25565 falla siempre.
   - fuente: Método: nslookup -type=SRV _minecraft._tcp.quemandan.minehost.pro 1.1.1.1 (respuesta: priority 1, weight 1, port 25445, target sv36.minehost.pro) y getaddrinfo del host base falla.
   - notas: Verificado hoy. El launcher tiene que resolver SRV (o el manifest debe traer host:puerto reales) y hacer el Server List Ping al target. Ojo: Minehost puede cambiar sv36/puerto; mejor que host:puerto vengan del manifest/backend, no hardcodeados.

5. [high] Estado real del server hoy (Server List Ping a sv36.minehost.pro:25445): version name '26.1', protocol 775, 0/20 jugadores, MOTD 'A Minecraft Server' (default), favicon presente, TCP connect 32 ms desde la PC del usuario (IP 45.235.98.223, hosting en Argentina).
   - fuente: Método: handshake status (packet 0x00 state=1) implementado en Python contra 45.235.98.223:25445.
   - notas: Verificado hoy. Útil para el launcher: el SLP da jugadores online/max gratis (mostrar '3/20 online' en la home). La web minehost.pro respondió HTTP 522 (Cloudflare: origen caído) durante toda la sesión: no pude verificar qué ofrece el panel (RCON/SFTP/API). Eso es además una señal de riesgo del proveedor.

6. [high] En offline-mode el servidor ignora el UUID que manda el cliente y genera uno propio: UUID v3 = MD5('OfflinePlayer:' + username), sensible a mayúsculas. El UUID que TLauncher le dio a PEPE (5b071e1f-3a11-4f28-9c68-a6321cadc031) es v4 aleatorio y NO es el UUID con el que el server guarda su inventario; el server usa 7a067f19-b48d-3c6e-9039-8f37f64def1f.
   - fuente: https://minecraft.wiki/w/Universally_unique_identifier (cita: 'the unique identifier chosen for offline mode players is UUID version 3, generated from the MD5 hash of OfflinePlayer:<username>'); cálculo propio en Python de md5('OfflinePlayer:PEPE') con bits de versión 3.
   - notas: Verificado hoy. Consecuencia directa para el plan: 'identidad = UUID interno del launcher' no sirve como identidad en el servidor. La identidad server-side es el username exacto. UUIDs offline calculados: PEPE 7a067f19-b48d-3c6e-9039-8f37f64def1f, Chichon 5f1bb3e1-3a21-3c39-a409-e50842f7df31, Titit0N 7bc394ba-c092-3432-b0b3-57a16c894f33, Luquitas1410 9c4d6396-daf9-3c3c-9eb3-93fe87cb87b7. 'Pepe' o 'pepe' darían otro UUID y otro inventario.

7. [high] Migración sin perder inventarios: los usernames del launcher deben ser byte-a-byte iguales a los actuales (PEPE, Chichon, Titit0N, Luquitas1410 y el quinto). El plan no contempla reserva de nombres ni política de username compatible con Minecraft (3-16 chars, [A-Za-z0-9_], sin espacios), ni inmutabilidad del nombre.
   - fuente: Derivado del punto anterior (UUID offline = f(username)) y de los hechos verificados en la PC (command_history).
   - notas: Corrección: pre-crear/reservar las 5 cuentas con el case exacto antes de abrir el registro; username inmutable (renombrar = perder inventario, salvo que el admin mueva el archivo playerdata/<uuid>.dat); validar regex de Minecraft en el registro; comparar unicidad case-insensitive para evitar 'Pepe' vs 'PEPE'.

## Riesgos
- Riesgo legal/reputacional: el server offline-mode con jugadores sin licencia está en zona gris de la EULA ('let other people get access... in a way that is unfair or unreasonable'); baja probabilidad de acción contra 5-20 amigos, pero el proyecto no debe publicitarse ni parecer oficial.
- Riesgo de identidad: un error de mayúsculas en un username (Pepe vs PEPE) o un rename genera otro UUID offline y 'pierde' el inventario; sin EasyAuth cualquiera con TLauncher entra con el nombre de otro.
- Riesgo de proveedor: minehost.pro estuvo con HTTP 522 toda la sesión; el hostname del server no tiene A record y depende de SRV hacia sv36:25445 que Minehost puede cambiar; no se pudo verificar si hay RCON/SFTP/API (define si la whitelist automática es posible).
- Riesgo de deriva de versiones: Mojang ya está en 26.2 y los mods tienen builds 26.2; sin pin estricto y proceso coordinado server+manifest, un update parcial rompe la entrada al server.
- Riesgo de distribución: sin firma de código, cada .exe nuevo dispara SmartScreen; sin auto-update desde la v1, cada bug obliga a reinstalar a mano a todos.
- Riesgo de stack: C# + WPF + ASP.NET es curva nueva para un dev TS; si además el panel va dentro del .exe, el mantenimiento a largo plazo recae en el stack menos conocido.
- Riesgo de UX: pisar options.txt/xaero/keybinds en cada actualización o no importar desde TLauncher hace que los 5 jugadores rechacen el launcher en la primera semana.
- Riesgo de licencias solo si se re-hostean archivos (Xaero ARR con condiciones, Sodium PolyForm Shield, Complementary Agreement 1.3); se elimina descargando desde Modrinth y dando créditos.
- Riesgo de doble contraseña (launcher vs /login de EasyAuth) si no se define la sincronización o se acepta explícitamente que son distintas.
